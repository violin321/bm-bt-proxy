# LTX 无码优选接入

2026-11-08，Asia/Shanghai。用户已在其 Byte-Muse 使用“仅无码”，希望同番号优先下载 LTX 模型破解版本。

## 接入方式

在 BM-BT 的“设置 → 连接 Byte-Muse”选择“LTX 优选 · 仅无码”，复制生成的配置。关键值为：

```yaml
BT_URL: "http://bm-bt-proxy:8000/api/torrents/ltx"
BT_METHOD: "get"
BT_HEADER: "{}"
BT_JSON_DATA: ""
DEFAULT_SORT: "uc"
```

地址须从实际 Byte-Muse 实例可达；启用 API Key 时使用页面主动复制的真实 `BT_HEADER`，不要照抄此处空对象。保留已有“仅无码”、大小、UHD 和其他下载筛选；实际生效的默认排序 `DEFAULT_SORT` 也需使用 `uc`，否则旧的免流、中字、站点或做种数排序仍可能覆盖 LTX 顺序。此方案调整版本偏好：LTX 优先于原有质量、站点、做种排序，下载硬筛选仍先执行。

`GET/POST /api/torrents/ltx` 与 `/bt/api/ltx` 沿用原 API Key 认证，公开响应仍只有 `{data:[...]}`。标准 `/api/torrents` 和 `/bt/api`、源配置与原排序偏好保持原行为。

## 行为

- 专用接口只保留严格 `uc=true` 的资源；单独出现 LTX 不会伪造 UC 属性。没有无码资源就返回空结果。
- 识别单条资源 `tags` / `labels` 中的明确 LTX 标记，以及标题中的独立 LTX、LTX-V3.2 等标记。不会把同片共享 `genres`、源分类、源名称或普通“无码破解”当作 LTX 版本。标记说明上游自述，不验证实际使用模型。
- 专用方案先保留有 LTX 标记的完整无码记录作为同哈希重复项的胜出者，同档再按源优先级、配置顺序选择；不会拼接不同记录的旗标或标签。同哈希记录若大小/UHD元数据相互冲突，只保留胜出记录，不保证保留丢弃项的过滤结果。标准方案仍使用原源优先级去重。
- LTX 档先于其他无码档；同档内仍应用已保存的 BM-BT 返回顺序，然后源优先级及原顺序。只排序，不在 BM-BT 提前丢掉其他无码候选。
- Byte-Muse 继续先执行下载条件筛选，再稳定排序。实际生效的默认排序使用 `uc` 时，候选均为 UC，保持接口顺序：可用 LTX 优先；若 LTX 被大小、UHD 等筛掉，其他合格无码自然兜底；若所有候选都被筛掉，该 Byte-Muse 版本会把首条候选标记为不合格交给既有刷流流程，不能把大小/UHD筛选视为保证不下载的限制；BM-BT 不改变这个上游行为。若需所有候选不合格时停止，应在 Byte-Muse 订阅选择“严格模式”（内部值必须为大写 `STRICT`）；合成调用验证此时无下载或通知。
- 这样避免“只返回 LTX 后，LTX 被消费端筛掉，反而丢失合格无码兜底”的问题。无需在 BM-BT 复制每条订阅的过滤条件，也不借用 `free`、`seeders`、`site` 传递伪造排序权重。

“搜索与测试”增加“返回方案”，可对真实源试查并查看 LTX 条数、保留无码条数及每条资源的标记来源；该选择和接入方案下拉框只影响当前测试或生成配置，不写生产设置，不触发订阅或下载。
