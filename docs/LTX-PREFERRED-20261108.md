# LTX 无码优选接入

2026-11-08，Asia/Shanghai。用户已在其 Byte-Muse 使用“仅无码”，希望同番号优先下载 LTX 模型破解版本。

## 接入方式

在 BM-BT 的“设置 → 连接 Byte-Muse”选择“LTX 优选 · 仅无码”，复制生成的配置。关键值为：

```yaml
BT_URL: "http://bm-bt-proxy:8000/api/torrents/ltx"
BT_METHOD: "get"
BT_HEADER: "{}"
BT_JSON_DATA: ""
DEFAULT_SORT: "uc"
```

地址须从实际 Byte-Muse 实例可达；启用 API Key 时使用页面主动复制的真实 `BT_HEADER`，不要照抄此处空对象。保留已有“仅无码”、大小、UHD 和其他下载筛选；实际生效的默认排序 `DEFAULT_SORT` 也需使用 `uc`，否则旧的免流、中字、站点或做种数排序仍可能覆盖 LTX 顺序。此方案调整版本偏好：LTX 优先于原有质量、站点、做种排序，下载条件先执行，全部不合格后的行为由订阅模式决定。

`GET/POST /api/torrents/ltx` 与 `/bt/api/ltx` 沿用原 API Key 认证，公开响应仍只有 `{data:[...]}`。标准 `/api/torrents` 和 `/bt/api`、源配置与原排序偏好保持原行为。

## 行为

- 专用接口只保留严格 `uc=true` 的资源；单独出现 LTX 不会伪造 UC 属性。没有无码资源就返回空结果。
- 识别单条资源 `tags` / `labels` 中的明确 LTX 标记，以及标题中的独立 LTX、LTX-V3.2 等标记。不会把同片共享 `genres`、源分类、源名称或普通“无码破解”当作 LTX 版本。标记说明上游自述，不验证实际使用模型。
- 专用方案先保留有 LTX 标记的完整无码记录作为同哈希重复项的胜出者，同档再按源优先级、配置顺序选择；不会拼接不同记录的旗标或标签。同哈希记录若大小/UHD元数据相互冲突，只保留胜出记录，不保证保留丢弃项的过滤结果。标准方案仍使用原源优先级去重。
- LTX 档先于其他无码档；同档内仍应用已保存的 BM-BT 返回顺序，然后源优先级及原顺序。只排序，不在 BM-BT 提前丢掉其他无码候选。
- Byte-Muse 继续先执行下载条件筛选，再稳定排序。实际生效的默认排序使用 `uc` 时，候选均为 UC，保持接口顺序：可用 LTX 优先；若 LTX 被大小、UHD 等筛掉，其他合格无码自然兜底；若所有候选都被筛掉，该 Byte-Muse 版本会把首条候选标记为不合格交给既有刷流流程，不能把大小/UHD筛选视为保证不下载的限制；BM-BT 不改变这个上游行为。若需所有候选不合格时停止，应在 Byte-Muse 订阅选择“严格模式”（内部值必须为大写 `STRICT`）；合成调用验证此时无下载或通知。
- 这样避免“只返回 LTX 后，LTX 被消费端筛掉，反而丢失合格无码兜底”的问题。无需在 BM-BT 复制每条订阅的过滤条件，也不借用 `free`、`seeders`、`site` 传递伪造排序权重。

“搜索与测试”增加“返回方案”，可对真实源试查并查看 LTX 条数、保留无码条数及每条资源的标记来源；该选择和接入方案下拉框只影响当前测试或生成配置，不写生产设置，不触发订阅或下载。

本地可见 Microsoft Edge 在真实 BM-BT 和合成资源源上通过 5 组检查：标准/LTX 接入配置生成、路径前缀与密钥遮挡、原标准查询与 LTX 查询、标记来源、四种宽度无溢出和不修改设置。物理手机及实际下载不在验证范围。证据：`frontend-verification/ltx-browser-results.json`。

用户实际 Byte-Muse 位于局域网群晖 NAS；按用户要求先在 OVH 测试实例验收，不把 OVH 实例误当成其实际消费端。保留原有过滤条件，不触发实际下载。

OVH 隔离候选镜像：82 项通过，4 个启用源全部成功；示例返回 6 条去重无码，其中 2 条有资源级 LTX 标记。同一份真实响应的标准聚合与 1.8.0 完整相同。消费端合成检查另见 `frontend-verification/ltx-consumer-results.json`，覆盖 360 组稳定排序、64 种过滤组合、严格模式及调用者副作用 mock。

OVH 测试实例的真实 BT 客户端已解析上述 6 条资源，UHD筛选保留 5 条，`DEFAULT_SORT=uc` 保持接口顺序，严格模式最终选中有 LTX 标记的资源。使用临时内存配置；持久设置、订阅和下载未改变。

## 用户 NAS 接入

已将用户实际群晖 Byte-Muse 的 `BT_URL` 改为 BM-BT 的 `/api/torrents/ltx`，`DEFAULT_SORT` 改为 `uc`。原 `BT_HEADER`、请求方式、“仅无码”及所有其他过滤条件、凭据和订阅设置均保留。Compose 中原本也固定了 `BT_URL`，已同步更新，并固定为当前同一镜像的摘要引用；只重建 Byte-Muse，端口、挂载、网络和其他容器保持。订阅数据库仅做在线备份，不回写。

只读读取 NAS 正在运行服务的 `/api/v1/config`，确认排序为 `["uc"]`、接口路径为 `/api/torrents/ltx`、“仅无码”为开启。已登录的 Edge 页面也确认“仅无码”保留。NAS 未执行资源搜索、手动订阅或下载；真实查询和消费端选择验证均在 OVH 完成。配置与 Compose 的原文件、当前文件校验值、在线数据库备份和主机端单服务回滚脚本均已保留。

Byte-Muse v1.32.0 的排序页面会补齐显示八种规则，这个显示不代表服务器启用了八项排序；当前实际值仍只有 `uc`。点击排序的“上移/下移”再保存，会把补齐后的排序列表作为新规则提交，可能覆盖 LTX 优先所需的保序设置。使用本方案时保留 `DEFAULT_SORT=uc`；不要通过移动这些项目重新排序。仅因页面显示八项无需重新配置或重建容器。

脱敏后的正式部署、OVH 客户端、公网浏览器和 NAS 配置证据见 `frontend-verification/ltx-release-results.json`，按执行阶段分别记录；早期 OVH 阶段的“NAS 未改动”不表示最终没有完成 NAS 接入。
